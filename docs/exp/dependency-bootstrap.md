# 经验之谈：临时验证环境与依赖准备

### 新版 pnpm 自动切换项目版本时，卡住可能发生在安装依赖之前

- **现象**：宿主 pnpm 与 packageManager 声明版本不同，执行安装后长时间没有项目依赖进度；旧版的 manage-package-manager-versions 参数也不被识别。
- **根因**：本次 pnpm 12.14 会先准备项目指定的 12.6，再执行安装；切换工具自身版本和下载项目依赖是两个阶段。
- **规避/解决**：先辨别卡在哪个阶段。仅为本地临时验证、确认同主版本兼容时，可用 `pnpm with current` 执行命令，安装仍使用 frozen-lockfile，不修改 packageManager 或锁文件；ignore-scripts 只用于本次不需运行安装脚本的环境。正式环境仍遵守仓库锁定版本。
- **来源**：2026-10-30，编排自动更新功能验收，pnpm 本地命令验证。

### 官方依赖大文件下载缓慢时，手工缓存也必须验证完整性

- **现象**：Go 工具链、SQLite/压缩库模块及 Iconify 大包下载长时间停滞；把临时下载文件 rename 到缓存时还出现跨文件系统错误。
- **根因**：本次网络对单连接大文件传输很慢；临时目录与缓存目录可能不在同一文件系统。pnpm 的 store add 本地压缩包也不能替代 registry 包的元数据记录。
- **规避/解决**：先查实际下载进度和官方源连通性，避免反复重装。确需手工补缓存时，仅从官方源获取；使用 Range 并发下载须校验各段范围、总长度及完整归档，npm 包须匹配锁文件完整性，Go 模块仍须经 go.sum 校验。落缓存先复制到目标目录的临时文件再同目录 rename，不能假定跨目录 rename 一定可用。用于验证的本机缓存服务完成后关闭，不改仓库源配置。
- **来源**：2026-10-30，编排自动更新功能验收，官方 Go module proxy/npm 归档下载及本机缓存验证。
